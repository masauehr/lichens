# 管理方式の検討メモ

作成日: 2026-05-06

## 選択肢の比較

### 選択肢A: GitHub管理（Markdownベース）

**利点**
- バージョン管理（変更履歴が残る）
- GitHub上でMarkdown・画像が綺麗に表示される
- 全文検索が可能（`grep` / GitHub検索）
- 無料・スマホからも閲覧できる
- Claude Codeとの親和性が高い（自動化しやすい）

**課題**
- 画像ファイルが大きいと容量を圧迫（Git LFS検討）
- GitHubの無料プランは容量制限あり（1リポジトリ1GB推奨）
- 非エンジニアには操作ハードルが高い

**画像容量の試算**
- 1枚あたり3〜8MB（JPG 12MP）
- 100枚 → 約300〜800MB（ギリギリOK）
- 500枚 → 要Git LFS（無料枠: 1GB）

---

### 選択肢B: PDF化

**利点**
- 印刷・配布が容易
- ビューアを問わず同じ見た目で表示
- 保存性が高い（アーカイブ向き）

**課題**
- 更新のたびに再生成が必要（自動化しないと大変）
- 全文検索は可能だが構造的なフィルタリングが難しい
- バージョン管理がしにくい

---

### 選択肢C: ハイブリッド（GitHub + PDF出力）

- **日常管理**: GitHub上のMarkdownで運用
- **配布・印刷時**: スクリプトでPDFを生成

→ 実質このアプローチが最もバランスが良い。

---

## 現時点の方針決定

> **GitHub管理をメインとし、必要時にPDFを出力するハイブリッド方式を採用**

### 理由

1. 地衣類写真の枚数は当初少ない（〜100枚程度）なのでGitで十分管理できる
2. Markdownは更新が容易でClaude Codeとの相性が良い
3. PDF出力は `pandoc` で後から自動化できる

### Git LFS 移行のトリガー

以下のいずれかに達したら Git LFS を検討する:
- 画像ファイルの合計が **500MB** を超えた
- 1回のコミットで **100MB** 以上の画像を追加した

## 家族写真への横展開メモ

このプロジェクトで検証したいこと:

| 検証項目 | 内容 |
|---------|------|
| メタデータ構造 | 撮影日・場所・タグ・人物タグ（家族写真では人物名）の管理 |
| 画像容量 | 家族写真は枚数がはるかに多い → Git LFSか別ストレージが必須 |
| 閲覧性 | GitHub表示で十分か、静的サイト（GitHub Pages）が必要か |
| アクセス制御 | 家族写真はprivateリポジトリ必須 |
| 自動化 | 写真アプリ → 自動インポートのスクリプト化 |

### 家族写真向けの代替ストレージ候補

| サービス | 容量 | 費用 | GitHub連携 |
|---------|------|------|-----------|
| iCloud | 200GB〜2TB | 月130〜400円 | なし |
| Google Photos | 15GB無料〜 | 月250円〜 | なし |
| Backblaze B2 + Git LFS | 無制限 | 容量従量 | ○ |
| Cloudflare R2 | 10GB無料〜 | 容量従量 | ○ |

→ 地衣類プロジェクトは当面GitHub直接管理で進め、課題が見えたら判断する。
